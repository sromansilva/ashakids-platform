## 01. Dictamen ejecutivo

**El flujo está parcialmente alineado.** El seguimiento por hijo y los contratos de citas, sesiones, reportes y mensajes de texto existen; faltan requisitos expresos de reserva, directorio, filtros, modales y aprendizaje persistido. Esta revisión no implementa esas diferencias.

| Pantalla | Coincidencia actual | Diferencia con el texto |
| --- | --- | --- |
| /padre | Selección por ID, seguimiento, botones, contadores e hitos | Contadores desde sesiones; próxima cita incluye pendientes; reporte en tarjeta, sin modal |
| /padre/camino | Misma base, cuatro pestañas y datos por hijo | Hitos por existencia actual, sin registrar primera fecha; detalles desplegables |
| /padre/agenda | Paciente, tratamiento activo, modalidad; POST de reserva | Fin manual, tratamiento obligatorio, terapeuta derivado; sin disponibilidad anticipada; ubicación siempre visible |
| /padre/psicologos | Selección del hijo y acceso a agenda | Lista tratamientos asignados; sin directorio de todos los terapeutas ni modal profesional |
| /padre/mensajes | Conversaciones por tutor/profesional y texto persistido | Sin imágenes/audio ni API de adjuntos; actualización manual |
| /padre/reportes | Sesiones y reporte/PDF mediante detalle | Mantiene valoración; sin filtro mensual; incluye sesiones sin reporte y de todos los meses; sin modal |
| /mundo-asha | Prototipos navegables y selección del hijo | Cuatro mundos propuestos, prototipos separados, sin URL por nivel ni progreso conectado |

Los resultados son observaciones de código y metadatos actuales, apoyadas por 55 pruebas frontend con HTTP simulado. No certifican un recorrido real de extremo a extremo ni las filas de un usuario concreto.

Sin cifras heredadas como pruebas nuevas, cambios de .env, usuarios nuevos, audio guardado o fixtures de integración destructivas. Se preservan los informes y evidencias anteriores.

## 02. Arquitectura y cambios realizados

React -> HTTP/JSON -> FastAPI -> SQLAlchemy -> PostgreSQL. Autenticación propia; sin conexión directa de React a Supabase ni Supabase Auth. Se añadieron únicamente informe, evidencia sanitizada y continuidad documental, sin modificar UI, contratos o BD.

El catálogo PostgreSQL confirma **26 tablas public**. information_schema expone 22 al rol runtime; has_table_privilege confirma que no puede SELECT en mundos, niveles, objetivos ni mensaje_adjuntos. Las cuatro tablas existen; no deben confundirse con tablas ausentes. Los permisos se revisarán al implementar sus funciones, sin conceder acceso indiscriminado.

Cadena clínica existente: tutores -> pacientes -> expedientes -> tratamientos -> reservas -> sesiones -> reportes_sesion. El tratamiento contiene el terapeuta; la reserva copia paciente/profesional y referencia el tratamiento.

## 03. Identidad, pacientes y pasos omitidos

| Punto | Hallazgo confirmado | Consecuencia para el texto |
| --- | --- | --- |
| Alta del hijo | El modal actual llama POST /pacientes; crear_paciente no crea Perfil | No garantiza paciente + PERFILES. El endpoint /padres/hijos sí crea ambos; unificar comportamiento antes de usar sus métricas |
| PERFILES | Se crea/serializa en la API de padres, pero cerrar_sesion no actualiza sus contadores | No cambiar contadores a perfiles.sesiones_totales sin definir y sincronizar el significado; podría permanecer en cero |
| Tratamiento | POST /tratamientos exige ADMIN, abre expediente si falta y asigna terapeuta | El texto atribuye la asignación al terapeuta; hoy la realiza administración y concede acceso a la familia |
| Progreso médico | La UI muestra Sin medición; perfil se describe como gamificado/formativo | Definir evaluación clínica, fecha y autor si se requiere progreso médico; no inferirlo de sesiones o experiencia |

Flujo operativo actual que debe explicitarse: registrar hijo -> administración asigna tratamiento/profesional y expediente -> padre solicita reserva PENDIENTE -> profesional confirma -> profesional registra sesión PROGRAMADA -> inicia EN_CURSO -> finaliza con asistencia -> guarda reporte -> padre consulta y descarga.

El reporte también puede guardarse EN_CURSO. Si el requisito es mostrar exclusivamente el de la última sesión asistida y finalizada, filtrar por ambos estados; el seguimiento actual solo exige reporte_disponible. Las pantallas de evaluación/consentimiento existentes no constituyen pasos clínicos persistidos certificados en este corte.

## 04. Citas, sesiones y reportes

| Requisito del equipo | Estado actual y evidencia | Trabajo necesario |
| --- | --- | --- |
| Duración fija 45 minutos | CitaHorario exige inicio y fin; solo valida fin posterior. BookingDialog permite ambos | Calcular fin en servidor y UI; misma regla para reprogramación. Retirar campo manual |
| Tratamiento opcional | Modelo, CitaCrear y SQL real: reservas.id_tratamiento NOT NULL | Requiere contrato y migración revisados; validar paciente/profesional explícitos y permisos para primera consulta |
| Elegir terapeuta activo | crear_cita lo obtiene del tratamiento; no hay selector independiente | Directorio autorizado y regla: tratamiento elegido debe corresponder al paciente y profesional |
| Disponible/no disponible | validar_horario detecta solapamiento de paciente o profesional al guardar | API de disponibilidad sin datos privados; mantener comprobación transaccional al guardar |
| Solo sesiones confirmadas bloquean | Hoy cualquier reserva distinta de CANCELADA bloquea, incluidas PENDIENTES | Acordar si solicitudes pendientes ocupan horario; evitar doble reserva al cambiar la regla |
| Ubicación solo presencial | Campo visible con ambas modalidades | Mostrar/validar presencial; limpiar valor al pasar a virtual según contrato |
| Próxima cita confirmada | summarizeFamily admite PENDIENTE/CONFIRMADA y prioriza EN_CURSO | Filtrar confirmadas para ese card; mostrar solicitudes pendientes por separado si se desea |
| Último reporte en modal | Resumen muestra cuatro campos en tarjeta; historial usa desplegable | Modal con navegación/cierre; elegir criterio de último por sesión asistida o fecha de publicación |
| Mes actual e históricos | /reportes lista todas las sesiones familiares; progreso es pendiente | Filtrar reportes disponibles, separar mes actual/histórico y añadir mes/año. No exige inventar una entidad de evaluación mensual |

Persistencia de citas en reservas está implementada en crear_cita. **No se creó una cita real en esta revisión**: no se presenta la inspección SQL como una nueva prueba de escritura.

No existen columnas de título en reservas o reportes_sesion. Si el texto exige título, acordar etiqueta derivada (por ejemplo, sesión/fecha) o contrato nuevo. Los hitos comprueban existencia actual; no almacenan primera ocurrencia histórica. /padre/damino es un error tipográfico: la ruta real es /padre/camino.

## 05. Tablas sin flujo funcional y capacidades faltantes

| Tabla/grupo | Uso real encontrado | Paso por definir o implementar |
| --- | --- | --- |
| perfiles | Modelo y API de padres; no consumido por contadores actuales, alta actual no lo garantiza | Alta consistente; sincronización de sesiones; separar avance educativo y clínico |
| actividades | Consulta defensiva al impedir borrado de paciente; sin CRUD educativo | Profesional asigna tarea al niño; estado y consulta familiar |
| objetivos | Sin modelo/API operativa del núcleo; FK a actividades | Objetivos por actividad y resultados. objetivos_trabajados del reporte es texto, no relación a esta tabla |
| mundos, niveles | Catálogo hardcoded en React, sin modelos/API de catálogo | Publicar cinco mundos acordados y rutas por nivel; validar acceso/desbloqueo en servidor |
| resultados_nivel | Solo consulta defensiva de dependencias; sin registrar intentos | Guardar intento por paciente/nivel y recuperar después de recarga u otro dispositivo |
| logros, perfil_logros | Modelos/relación; se revisan al impedir borrado, sin concesión automática | Definir requisitos, otorgamiento y consulta si forman parte del alcance educativo |
| mensaje_adjuntos | Existe en SQL; sin modelo, endpoint, subida ni vista de archivos | Carga privada, vinculación al mensaje, formatos/tamaño y descarga autorizada. El nombre real es plural |
| evaluaciones_ia | Solo control defensivo al borrar; sin pipeline de IA | No es paso obligatorio del texto; IA permanece excluida del plan vigente |

No son tablas para borrar por no aparecer en una pantalla. Hay tablas de soporte activas: usuarios, roles, usuario_roles, sesiones_autenticacion, administradores y auditoria_cambios; sustentan identidad, administración y trazabilidad. Las tablas clínicas y conversaciones/mensajes sí tienen servicios operativos.

**Dependencia educativa omitida:** el esquema actual es pacientes -> actividades -> mundos -> niveles; objetivos depende de actividades y resultados_nivel une paciente/nivel. Cada mundo exige id_actividad y cada actividad pertenece a un paciente. Antes de usar cinco mundos como catálogo compartido, decidir cómo se relacionan catálogo y asignaciones individuales; no insertar mundos sin revisar esta dependencia.

Las rutas /mundo-asha/cuentos, canciones, adivinanzas, trabalenguas y juegos son rutas frontend, no endpoints de API educativa. /laberinto sigue presente y usa un componente distinto de /trabalenguas: eliminarlo es una consolidación solicitada, no una duplicidad idéntica confirmada. deriveWorldProgress contiene un cálculo puro, pero la pantalla pasa null y no publica niveles navegables/desbloqueados.

Pagos: fuera del alcance docente. Conservar solo demostración identificada cuando corresponda, sin convertirla en condición de reserva/sesión/reporte.

## 06. Seguridad y reglas que deben conservarse

| Prioridad | Hallazgo o dependencia | Acción propuesta |
| --- | --- | --- |
| Alta | Cita sin tratamiento cambia la asignación que hoy limita acceso clínico | Definir permisos de primera consulta y de terapeuta antes de migrar; reservar no debe exponer historia ajena |
| Alta | Desbloqueo educativo solo calculado localmente, sin contrato activo | Autorizar nivel por niño en servidor, incluida URL directa; guardar/validar intentos con regla aceptada |
| Alta | Adjuntos y catálogo carecen de SELECT runtime y APIs | Implementar flujo/permisos acotados conjuntamente; no habilitar permisos globales por esta revisión |
| Media | Conteos de perfil sin actualización y alta divergente | Corregir invariantes antes de tratar perfiles como fuente de métricas |

Mensajería existente: un chat tutor/terapeuta, compartido por hijos de esa familia. Inicio/envío requiere tratamiento activo y participantes habilitados; el historial puede quedar en solo lectura. El padre no obtiene todos los profesionales por este contrato. Añadir si el texto exige conversar antes de recibir tratamiento.
