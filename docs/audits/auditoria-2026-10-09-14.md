## 02. Arquitectura y cambios realizados

React -> HTTP/JSON -> FastAPI -> servicios/Pydantic -> SQLAlchemy/asyncpg -> PostgreSQL. Se conservan autenticación propia, Argon2id, sesiones opacas hasheadas y cookie HttpOnly. Sin Supabase Auth ni conexión SQL desde React. ADR0010 documenta la separación entre rol de aplicación y rol PostgreSQL del backend; ADR0009/TLS y limitador se conservan.

El inventario aprobado está en scripts/b02_role_inventory.py. apply_b02_runtime_role aplica CREATE ROLE, CONNECT de la BD configurada, USAGE de public y grants por tabla en una transacción. Crea políticas por operación exclusivamente TO ashakids_runtime y USAGE solo en secuencias dependientes de tablas con INSERT. Aborta si el rol existe; no es una migración automática al arrancar FastAPI. La contraseña aleatoria se deriva a un verificador SCRAM para el DDL; ningún secreto se publica.

| Grupo de tablas | Acceso aprobado y comprobado | Límite |
| --- | --- | --- |
| usuarios, sesiones_autenticacion, pacientes, perfiles | SELECT, INSERT, UPDATE, DELETE | DELETE en contratos protegidos; ejecución física sin ensayo. |
| usuario_roles, administradores | SELECT, INSERT, DELETE | Sin UPDATE ni administración de roles PostgreSQL. |
| tutores, terapeutas | SELECT, INSERT, UPDATE, DELETE | Edición de cuentas nuevas probada; no identidades anteriores. |
| expedientes, tratamientos, reservas, sesiones, reportes_sesion, conversaciones | SELECT, INSERT, UPDATE | No eliminación de historial clínico/chat. |
| mensajes, auditoria_cambios | SELECT, INSERT | Sin UPDATE/DELETE. |
| roles, logros, perfil_logros, actividades, resultados_nivel, evaluaciones_ia | SELECT | Sin escrituras de catálogo/educativas nuevas. |
| mundos, niveles, objetivos, mensaje_adjuntos | Sin permisos de tabla | Fuera del inventario actual. No GRANT ALL. |

SELECT/DELETE usan USING true; INSERT usa WITH CHECK true; UPDATE usa ambas. Esas políticas habilitan al servidor para aplicar sus reglas y **no aíslan familias dentro de PostgreSQL**. FastAPI sigue validando sesión, rol y pertenencia/asignación de cada recurso. El runtime no tiene propiedad, CREATE en BD/public, TRUNCATE, REFERENCES, TRIGGER, MAINTAIN ni UPDATE/SELECT de secuencias. ADMIN de AshaKids conserva cuentas, pacientes y tratamientos.

Se leyeron26 tablas/RLS,92 restricciones,71 índices y26 dependencias de secuencias en metadatos reales;19 modelos ORM no muestran diferencias. Las columnas visibles por information_schema para el rol nuevo son154, correspondientes a las tablas concedidas; no se reinterpretan las178 del propietario en corte13 como un resultado nuevo equivalente. No se añadieron tablas, columnas, índices o restricciones clínicas.

Coincidieron; no se revocaron ni ampliaron privilegios de identidades anteriores. Se excluyen del cotejo solo entradas del rol nuevo y sus posibles membresías automáticas como rol concedido; el runtime no pertenece a otros roles. Las políticas anteriores se conservaron y solo se añadieron las aprobadas.

PUBLIC conserva CONNECT/TEMP en la BD y USAGE de public; no tiene grants de tablas/secuencias ni CREATE de BD/public. NOINHERIT no elimina derechos de PUBLIC; no se alteran defaults compartidos. Las dos funciones SECURITY DEFINER con EXECUTE público en graphql no son alcanzables por el runtime porque carece de USAGE del schema. Se comprobó ausencia de funciones definer alcanzables combinando ambos permisos. No afirmar una denegación absoluta de objetos temporales o de conexiones heredadas de PUBLIC.

Los seis rechazos42501 son: SELECT LIMIT0 de mensaje_adjuntos, EXPLAIN sin ANALYZE de UPDATE/DELETE mensajes e INSERT roles, currval de secuencia logros no concedida y CREATE SCHEMA AUDITORIA_B02_DENIED. No se otorgó GRANT ALL ni acceso a funciones definer.

Solo DATABASE_URL cambió en .env; el resto de claves y destino se cotejaron iguales. Respaldo y contraseña runtime permanecen en tmp ignorado. El propietario conserva sus permisos fuera del runtime. Reversión preparada a la URL previa; no se presenta como restauración de backup probada. Fuente/evidencia no incluyen URL, contraseña, SCRAM, token, cookie ni datos clínicos reales.
