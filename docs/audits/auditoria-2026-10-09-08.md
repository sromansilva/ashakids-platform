## 03. APIs funcionando: identidad y pacientes

Se verificó el flujo completo de autenticación y autorización por roles (ADMIN, PADRE, TERAPEUTA) sobre la base local `ashakids_test_accept07_hq`:

| Método y ruta | Estado | Resultado |
| --- | --- | --- |
| POST /api/v1/auth/login | 200 / 401 | Sesiones emitidas para identidades válidas; rechazo ante clave errónea |
| GET /api/v1/usuarios | 200 / 403 | ADMIN lista cuentas; PADRE y TERAPEUTA reciben 403 Forbidden |

### Detalle de la incidencia del navegador

En este turno se levantó el servidor frontend de Vite en `http://127.0.0.1:5174/` y la API en `http://127.0.0.1:8001/`. Al delegar la aceptación al subagente de navegador con las instrucciones precisas para los roles ADMIN, PADRE y TERAPEUTA, la herramienta interna `open_browser_url` falló repetidamente:
```text
failed to run playwright manager: failed to install playwright: could not install driver: 
error: got non 200 status code: 404 (404 Not Found) from https://playwright.azureedge.net/builds/driver/playwright-1.57.0-win32_x64.zip
```
Siguiendo las directrices del proyecto y las instrucciones expresas del usuario ("Si ocurre nuevamente, no lo eludas cambiando puerto, origen o herramienta"), no se realizaron evasiones ni se simuló falsamente una interacción visual en el navegador. Las 232 pruebas unitarias de Vitest validan el montaje, renderizado, validación de formularios y manejo de errores de los componentes en jsdom, pero la interacción E2E en navegador real permanece formalmente como pendiente.

## 06. Seguridad, incidentes y límites

### Análisis del Incidente 01 histórico

En la auditoría inicial AUDIT-2026-10-08 / 2026-10-09-01, una ejecución no aislada de pruebas heredadas basadas en `unittest` (`test_admin_crud.py`, `test_pacientes_crud.py`) apuntó al puerto predeterminado 8000 (el cual conectaba a Supabase compartido), ejecutando creaciones y eliminaciones sobre cuentas de prueba (identificadas en los logs con IDs 44 y 45).

Estado y mitigaciones verificadas:
1. Las suites heredadas fueron inmediatamente deshabilitadas mediante `unittest.skip` condicionado a variables de entorno explícitas. En esta corrida se mantuvieron 25 pruebas omitidas.
2. Se implementaron guardas de tres capas:
   - `testing_database.py`: restringe las URLs de base de datos a `127.0.0.1` o `localhost` y exige prefijo `ashakids_test_*`.
   - `live_environment.py`: restringe la API de pruebas a `http://127.0.0.1:8001/api/v1` y valida coincidencia estricta de variables de entorno.
   - `verify_delivery_journey.py` (`confirm_api_database`): verifica directamente en la base de datos de PostgreSQL que el hash de sesión emitido por la API pertenezca a la instancia local antes de emitir la primera escritura clínica.
3. Impacto histórico en la base compartida:
   - Dado que los registros históricos carecían de marcas de tiempo por petición y no existía un snapshot de línea base anterior al incidente, el impacto residual en las cuentas de prueba de Supabase no ha sido modificado ni recalculado en este turno.
   - Se mantiene la recomendación al equipo de auditar directamente la tabla de usuarios en Supabase antes de la entrega final si esas cuentas de prueba se pretendían conservar.
